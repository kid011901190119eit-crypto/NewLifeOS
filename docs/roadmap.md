# 実装ロードマップ

LifeOSを「どの順番で作るか」と、各フェーズの「どこまでできたら完了とするか」をまとめた文書。何を作るかは [`spec.md`](spec.md)、作業のルールは [`../AGENTS.md`](../AGENTS.md) を正とする。この文書と仕様書が食い違った場合は仕様書を優先し、この文書を直す。

## 進め方の原則

- **フェーズは上から順に進める。** 前のフェーズの完了の条件を満たしてから次へ進む。順番を変えたいときはオーナーが判断する。
- **1つのフェーズを、複数の小さなプルリクエストに分ける。** 1フェーズ=1プルリクエストにはしない。
- **各フェーズで、初めて導入した技術の解説を `docs/learning/` に書く。** 設計判断をしたらADRを残す。
- **「未確定」の項目は推測で埋めない。** そのフェーズに入る前に、オーナーが決める。
- 構成要素はどれも学習のために意図的に入れている。「個人用には過剰」という理由で削らない(`AGENTS.md`「意図的な作り込み」)。

## フェーズ4: 家計簿の中核

**目的**: 家計簿のドメインロジックとデータの守りを、画面より先に作る。お金の計算が正しいことを、テストで保証する。

**主な作業**
- 画面入力から仕訳への変換(§5.3。フェーズ1で作った表をテストにする)
- 口座別・全口座の残高(確定残高と予定込み残高。FIN-04・FIN-05)
- 貸し借りと相手ごとの未精算額(FIN-03)
- 入力チェックと「要確認」の判定(FIN-08、§3.3.1 の4つのルール)
- DBの制約: 外部キー、CHECK制約、仕訳合計0の遅延制約トリガー(§5.1)
- 冪等キー: 同じキーでの再送は1件しか登録しない
- 取消は取消フラグか打ち消しの取引で表し、物理削除しない
- 変更履歴(CORE-04)と作成元の記録(CORE-06)、履歴の閲覧と取り消しの仕組み
- Transactional Outbox と BullMQ のワーカー(書き込みと同じトランザクションでイベントを記録し、ワーカーが配送する。§4.4)
- モジュールの登録の仕組み(`defineModule`、`packages/registry`、起動時の検査。`docs/design/module-system.md`)

**完了の条件**
- [ ] 仕訳変換・残高計算・入力チェックのユニットテストのカバレッジが90%以上(§10.1)
- [ ] §3.3.1 の4つのルールそれぞれについて、違反するとき・しないときのテストがある
- [ ] 合計が0にならない仕訳がDBに拒否されることを、Testcontainersの結合テストで確認している
- [ ] 同じ冪等キーで2回登録しても1件しか登録されないことを、結合テストで確認している
- [ ] 金額がすべて整数(`bigint`)で扱われ、浮動小数点型が使われていない
- [ ] 取消・取り消しの後も元の記録が残っている(物理削除していない)ことをテストで確認している
- [ ] すべての書き込みに作成元(`user` / `agent`)が記録され、変更履歴から取り消せる
- [ ] outboxに記録したイベントがワーカーから配送され、同じイベントを2回受けても結果が変わらない(冪等)ことをテストで確認している

**主に学ぶこと**: TDD、複式簿記の実装、DB制約、冪等性、Transactional Outbox、ジョブキュー

## フェーズ10: 観測性

**目的**: 何が起きているかを外から見えるようにし、異常に人が気づける状態にする。サーバーが丸ごと止まっても気づけるようにする。

**主な作業**
- OpenTelemetry で、ログ・メトリクス・トレースを各アプリから送る(OTel Collector)
- Prometheus(メトリクス)、Loki(ログ)、Tempo(トレース)、Grafana(ダッシュボード)を立てる
- Alertmanager で §7.1 のアラートを定義し、Discord に通知する
- インシデント一覧の画面(ADM-02。状態は「発生 → 確認済み → 解決」)
- AWS Lambda + EventBridge Scheduler による外部死活監視を OpenTofu で構築する(`infra/opentofu/aws`)。GitHub Actions から AWS へは OIDC で認証する
- AWS Budgets で、課金が発生したら通知する
- 主なアラートの対応手順を `docs/runbooks/` に書く

**完了の条件**
- [ ] 1つのリクエストを、画面 → API → DB までGrafana上のトレースでたどれる
- [ ] ログ・メトリクス・トレースがGrafanaで見られる
- [ ] §7.1 の各アラートについて、わざと異常を起こすとDiscordと管理画面のインシデント一覧の両方に届くことを確認している(バックアップと復元テストのアラートはフェーズ11で確認する)
- [ ] インシデントの状態を「発生 → 確認済み → 解決」と変えられる
- [ ] Oracleのサーバーを止めると、AWSの外部死活監視が検知して通知する
- [ ] AWSへの認証に長期のアクセスキーを使っておらず、AWS Budgetsの通知が設定されている
- [ ] 主なアラートの対応手順が `docs/runbooks/` にある

**主に学ぶこと**: 観測性の3本柱(ログ・メトリクス・トレース)、アラート設計、インシデント対応、外部監視、クラウドの課金管理

> 未確定: PWAのプッシュ通知の範囲。決まるまでは、通知はDiscordと管理画面のみとする。

## フェーズ11: バックアップ

**目的**: データを失わない仕組みを作り、「本当に戻せる」ことを定期的に確かめる。本番利用を始める(フェーズ12)前に必ず済ませる。

**主な作業**
- pgBackRest で、フルバックアップとWALアーカイブを取る(PITR)
- Oracle Object Storage と Cloudflare R2 の2か所に、暗号化して保存する(3-2-1ルール)
- 保持期間を設定する(日次を30日分、月次を12か月分)
- 週1回、別のコンテナに自動で復元し、件数と残高が一致するかを検証する。失敗したら通知する
- 管理画面にバックアップの状況を表示する(ADM-01)
- 復元の手順を `docs/runbooks/` に書き、実際にその手順で復元してみる

**完了の条件**
- [ ] 2か所(別の事業者)に、暗号化したバックアップが保存されている
- [ ] 保持期間が日次30日分・月次12か月分に設定されている
- [ ] 任意の時刻の5分前以内の状態に戻せることを、実際の復元で確認している(RPO)
- [ ] 手順書どおりに、1時間以内に復旧できることを、実際の作業で確認している(RTO)
- [ ] 週1回の自動復元テストが動き、件数と残高の一致を検証している
- [ ] バックアップの失敗と復元テストの失敗が、Discordとインシデント一覧に通知されることを確認している
- [ ] 管理画面に、最終実行時刻・保持している世代・直近の復元テストの結果が表示される
- [ ] R2の使用量が無料枠(月10GB)の範囲に収まる見込みである

**主に学ぶこと**: バックアップの設計(RPO・RTO・3-2-1ルール)、WALとPITR、復元テストの自動化

## フェーズ12: 本番利用開始

**目的**: 家計簿を実際の生活で使い始める。

**前提**: フェーズ11が完了していること(データを失わない仕組みと、戻せることの確認が済んでいること)。

**主な作業**
- 本番環境で、口座とラベルを画面から登録する
- 開始残高を入力する(FIN-07)。口座ごとの残高と、その時点で未精算の貸し借りを、開始日付で1回だけ入力する
- 現行の家計簿(Notion版)の残高と一致するかを確認する
- 日常の記録を、LifeOS(画面とClaudeアプリ)で始める

**完了の条件**
- [ ] フェーズ11の完了の条件をすべて満たしている
- [ ] 開始残高を入力し、口座ごとの残高と未精算の貸し借りが、現行の家計簿と一致している
- [ ] 開始残高の入力後に、バックアップが取れていて、自動復元テストが成功している
- [ ] 実際の口座名・ラベル名・金額が、リポジトリ(シード、テスト、ドキュメント)に含まれていない

**主に学ぶこと**: 本番データの扱い、リリースの判断

> Notionからのデータ移行スクリプトは作らない(`spec.md` §2.2)。
