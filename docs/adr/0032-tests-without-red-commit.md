# 0032: Red のコミットを作れないテストは、わざと壊す実験でテストが落ちることを確かめ、プルリクエストの本文に書く(ADR 0029 を補う)

- ステータス: 承認
- 日付: 2026-11-06

## 背景
ADR 0029 で、テストを書く変更では Red と Green を別々のコミットにし、Red のコミットでは型の合う仮の実装のうえで、テストが期待値の違いで失敗する状態にすると決めた。

ところが、並列の試し(#46・#48)で、Red のコミットを作れないテストが2種類見つかった(Issue #50)。どちらも、仮の実装のままで、または実装が入った時点で、テストが最初から通ってしまう。

- (a)「正しい操作が拒否されない」ことを確かめるテスト(#46): たとえば「正しい行は制約に拒否されずに入る」ことを確かめるテスト。何もしない仮の実装(制約がない状態)では、そもそも何も拒否しないので、テストは通ってしまう。
- (b) すでに正しい実装に、あとから足したテスト(#48): 実装が先にあるので、テストを足した時点で通る。

ADR 0029 はこの2つの扱いを決めていなかった。Red のない変更を不合格にするのか、別の方法で確かめるのかが、実装役とレビュー役で食い違うおそれがある。

## 検討した選択肢
- わざと壊す実験で代える(実装を一時的に壊してテストが落ちることを確かめ、元に戻し、内容をプルリクエストの本文に書く): テストが期待値の違いで落ちることを確かめられる。AGENTS.md「4. 確かめる」とレビュー役の手順にすでにある方法なので、新しい道具や手順が要らない / コミットの履歴からは確かめられず、本文の記録とレビュー役の再実験に頼る
- 人工的な Red を作る(わざと誤った仮の実装を書いてコミットする。(b) では正しい実装を一度消すコミットを作る): ADR 0029 の形をそのまま保てる / わざと誤ったコードを書く手間がかかり、履歴が不自然になる。(b) では、すでに main にある正しい実装を消すコミットが作業ブランチに残る
- Red なしで、テストを足すだけにする: 手間がない / テストが本当に効いているか(失敗するべきときに失敗するか)を誰も確かめない

## 決定
- **ADR 0029 の決定は変えない。** 型の合う仮の実装で期待値の違いによる失敗を作れるテストは、これまでどおり Red のコミットを作る。
- 次の2種類のテストに限り、Red のコミットを作らなくてよい。
  - (a) 「正しい操作が拒否されない」ことを確かめるテストで、何もしない仮の実装では最初から通ってしまうもの
  - (b) すでに正しい実装に、あとから足したテスト
- その代わりに、**わざと壊す実験**を行う。実装を1か所だけ一時的に壊し(たとえば、拒否してはいけない値を拒否する条件を足す、正しい値を返す行を変える)、テストが期待値の違いで失敗することを確かめてから元に戻す。Turborepo のキャッシュから再生されていないことも確かめる(AGENTS.md「4. 確かめる」)。
- プルリクエストの本文に、テストごとに次を書く。
  - どのテストか、(a)(b) のどちらか、なぜ Red のコミットを作れないか
  - 何をどう壊したか
  - テストがどう失敗したか(期待値と実際の値の違いの要点)
  - 元に戻したこと
- レビュー役は、本文の記録を読み、同じ壊し方を自分のワークツリーで再現して、テストが期待値の違いで失敗することを確かめる。記録がない、または再現しても失敗しないときは不合格にする。

## 結果
- Red のコミットを作れないテストでも、テストが失敗するべきときに失敗することを確かめられる。
- 実装役とレビュー役が、Red のない変更を同じ基準で扱える。
- (a)(b) にあたらないテストまで「Red が作れない」として実験に逃げないよう、レビュー役は (a)(b) にあたるかも確かめる必要がある。
- 確かめた記録はコミットの履歴ではなくプルリクエストの本文に残るので、本文を書き忘れると確かめられなくなる。
