# 0014: モジュールのマニフェストをサーバー用と画面用に分け、一覧ファイルで静的に登録する

- ステータス: 承認
- 日付: 2026-11-04

## 背景
spec §4.3 では、モジュールが `defineModule` で自己紹介し、コアがそれを読み込むだけでモジュールを追加できる形を目指している。ただし `defineModule` の正確な型と、画面(UI)を登録する方法は未確定だった。画面はブラウザで動く SPA(ADR 0003)で、DB や Hono を含むサーバーのコードを読み込むことはできない。また、api・mcp・worker の複数のプロセスが同じモジュールの一覧を使う。

## 検討した選択肢
**マニフェストの数**
- サーバー用と画面用に分ける: ブラウザにサーバーのコードが混ざる事故が構造的に起きない / 定義が2か所になる
- 1つにまとめる(spec §4.3 の案): 1か所を見れば全体がわかる / 画面の部分を遅延読み込みにするなどの工夫がないと、サーバーのコードがブラウザ側に入り込む

**登録の方法**
- 一覧ファイルに手で書く(静的な登録): 何が登録されているかが一目でわかり、型チェックも効く / 追加のたびに1行書き足す
- ファイルを自動で探す(Vite の `import.meta.glob`): 書き足す作業が要らない / 仕組みが見えにくく、型の効き方が弱い
- 実行時に外から読み込む(Module Federation): モジュールごとに別々にデプロイできる / 仕組みが複雑で、モノリスには合わない

**サーバー側の一覧の置き場所**
- 共通の一覧を1か所(`packages/registry`)に置く: 追加の作業はこの一覧と画面の一覧の2行で済む / spec §10.2 にないパッケージが1つ増える
- プロセスごとに一覧を持つ: プロセスごとに載せるモジュールを変えられる / 追加のたびに4か所を書き換える必要があり、書き忘れが起きやすい

## 決定
- サーバー用の `defineModule`(`id`、`displayName`、`migrations`、`routes`、`tools`、`events`、`jobs`、`changeHandlers`)と、画面用の `defineModuleUi`(`id`、`displayName`、`menu`、`routes`)に分け、同じ `id` で結び付ける。`defineModuleUi` は、ブラウザで使える入口 `@lifeos/core/web` から出す。
- サーバー側の一覧は `packages/registry/src/server.ts`、画面側の一覧は `apps/web/src/modules.ts` に手で書く。api・mcp・worker・migrate は同じ一覧を読む。
- モジュールの `id` を、DBスキーマ名、API のパス(`/api/<id>`)、画面のパス(`/<id>`)、ツール・イベント・ジョブの名前の接頭辞として強制する。違反はコアの起動時の検査で止める。
- マイグレーションはモジュールごとのフォルダとスキーマに置き、適用履歴もスキーマごとに持つ。専用の `migrate` コマンドが `core` を先に、次に一覧の順に適用する。api・mcp・worker は起動時にマイグレーションを実行しない。
- 詳細は [`docs/design/module-system.md`](../design/module-system.md) を正とする。

## 結果
- モジュールを足す作業は、モジュールのパッケージを作り、2つの一覧に1行ずつ足すことで済む。既存のモジュールとコアのコードは変わらない(フェーズ9で検証する)。
- コアはモジュールを1つも import しないので、依存の向きが「モジュール → コア」の一方向に保たれる。
- 画面とサーバーの一覧がずれるおそれがあるので、アーキテクチャテストで `id` の一致を確かめる。
- `packages/registry` を spec §10.2 のリポジトリ構成に追加する。
- `migrate` コマンドをデプロイ時にどう呼ぶかは、フェーズ7で決める。
