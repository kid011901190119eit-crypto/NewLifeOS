# 0030: 家計簿のテーブル・制約・ビューは schema.ts に Drizzle で書き、データとトリガーは空のマイグレーションに手で書く。結合テストの DB は @lifeos/db/testing が本番と同じ migrateSchemas で作る

- ステータス: 承認
- 日付: 2026-11-06

## 背景
Issue #46 で、家計簿の4つのテーブル(`accounts`・`transactions`・`postings`・`idempotency_keys`)、DB の制約、システム勘定2件、ビュー `active_postings` を `finance` スキーマに作った(finance-data-model.md §3・§5)。次の Issue(#47)では、Drizzle では書けないトリガー(仕訳の合計0の遅延制約、書き換え・削除の禁止)を作る。そのため、次の点を決める必要があった。

- テーブル・制約・ビューと、データ(システム勘定)と、トリガー・関数を、それぞれどう書いてマイグレーションにするか。
- 結合テストで、finance のマイグレーションをどう適用するか。マイグレーションの適用(`@lifeos/db/migrate`)を import できるのは `apps/migrate` だけ、というルールがある(ADR 0027)。
- テストごとの DB の分け方、テストの書き方、Red の作り方(ADR 0029)。
- `bigint` の列を TypeScript でどう受け取るか(ADR 0028 では、金額は安全な整数の `number` で扱う)。

## 検討した選択肢
**テーブル・制約・ビューの書き方**(Issue #46 の補足でオーナーが決めた)
- `schema.ts` に Drizzle で書き、`drizzle-kit generate` で SQL を作る: 型と SQL が1か所からそろう。ビューも `pgView`(`financeSchema.view`)で書ける / Drizzle が書けない制約は別の方法が要る
- SQL をすべて手で書く: 何でも書ける / 型と SQL を二重に管理する

**システム勘定2件の INSERT・トリガーと関数**(同上)
- `drizzle-kit generate --custom` で作った空のマイグレーションに手で書く: 適用の順番と履歴が、ほかのマイグレーションと同じ仕組みで管理される / SQL を手で書くので、テストで確かめる必要がある
- アプリの起動時やシードのスクリプトで入れる: マイグレーションと分けられる / 適用の順番と「入れたかどうか」を別に管理することになる

**Red で作った制約のないマイグレーション(判断B)**
- Green で消し、制約つきで作り直す: main に入る形で、テーブルと制約が1つのマイグレーションにまとまる。Squash and merge なので main に途中の段階は残らない / 作業ブランチの上でファイルを消す
- 残して、制約を足す差分のマイグレーションを作る: 削除がない / テストの都合の「制約なし」の段階が、本番の履歴に残る

**結合テストの置き場所(判断A)**
- finance に置き、開発用の依存関係に `@lifeos/db`・`pg`・`@types/pg` を足す: テーブルの持ち主のそばにテストがある / 依存関係が3つ増える
- `apps/migrate` に置く: 依存関係が増えない / 適用と関係のないテストが migrate に混ざる

**テストでマイグレーションを適用する方法(判断F)**
- `@lifeos/db/testing` に「マイグレーションを適用した DB を作る」補助を足し、中で本番と同じ `migrateSchemas` を使う。testing から migrate への import だけを例外で許す: 本番と同じ処理でテストの DB を作れる / 境界のルールに例外が1つ増える。testing が本番のコードから import されると抜け道になる
- 補助を migrate の中に置く: ルールは変えない / finance のテストから使えない
- 補助の中で Drizzle の `migrate()` を直接呼ぶ: ルールを変えない / 本番と同じ処理を2か所に書き、片方だけ変わるおそれがある

**testing の抜け道の塞ぎ方(判断F の追加)**
- `@lifeos/db/testing` を import できるのをテストのファイル(`*.test.ts`)だけにする: 本番のコードから testing を経由して migrate に届かない / ルールが1つ増える
- 塞がない: ルールが少ない / 抜け道が残る

**テストごとの DB の分け方(判断C)**
- テストごとに空の DB を作り、マイグレーションを適用する: 「有効な開始残高は1件だけ」のような DB 全体の制約でもテスト同士が干渉しない / テスト1件ごとに数百ミリ秒かかる
- DB を1つだけ作って共有する: 速い / 開始残高のテスト同士がぶつかる
- 各テストを BEGIN〜ROLLBACK で包む: 速い / #47 の遅延制約はコミット時に動くので使えない

**テストの書き方(判断E)**
- `pg` で SQL を直接書く: どの INSERT が拒否されるかがそのまま見える。決められていない値も入れられる / テーブル定義の型はテストで使われない
- Drizzle の `insert` で書く: アプリと同じ書き方 / 決められていない値を入れるために型をごまかす必要がある

**apps/migrate の結合テストの期待値(判断D)**
- 適用件数を `3` に書き換える: 読みやすい / マイグレーションを足すたびに直す
- `_journal.json` の件数から求める: 今後直さなくてよい / 期待値の計算が1段増える

**bigint の受け取り方と範囲(判断G)**
- `mode: "number"` にし、金額と管理単位に安全な整数の範囲の CHECK を付ける: ADR 0028 と型がそろい、TypeScript で読んだときに値が変わる行を DB が入れない / 設計書の制約の一覧を直す
- `mode: "bigint"` にする: 範囲の心配がない / ADR 0028 の `number` と型が合わず、変換が要る
- `mode: "number"` だけにし、範囲の CHECK は付けない: 制約が少ない / 範囲外の値が入ると、読んだときに黙って丸められる

**Red で「正しい操作が拒否されないこと」のテストが通ること(判断H)**
- 認める: 制約を足しても正しい操作が拒否されないことを守るテストなので、制約のない状態で通るのが正しい / Red の報告に、通ったテストを一覧で示す必要がある
- Red で必ず失敗させる: すべてのテストの失敗を確かめられる / そのためだけに不自然な仮の実装が要る

## 決定
- テーブル・制約・部分UNIQUE インデックス・ビューは `packages/modules/finance/src/db/schema.ts` に Drizzle で書き、`drizzle-kit generate` でマイグレーションを作る。制約には名前を付ける。
- システム勘定2件(`開始残高`・`未分類`)の INSERT は、`drizzle-kit generate --custom` で作った空のマイグレーション(`0002_system_accounts.sql`)に手で書く。#47 のトリガー・関数も同じく空のマイグレーションに手で書く。
- Red で作った制約のないマイグレーションは、Green で消して制約つきで作り直す(B)。
- 結合テストは finance に置き、開発用の依存関係に `@lifeos/db`・`pg`・`@types/pg` を `packages/db` と同じ版で足す(A)。
- `@lifeos/db/testing` の `createMigratedDatabase` が、空の DB を作って本番と同じ `migrateSchemas` で適用する。dependency-cruiser と ESLint に、testing から migrate への import だけを許す例外を足す(F)。テストの補助は起動の処理ではないので、「起動のときにマイグレーションを流さない」というルールの目的は守られる。
- `@lifeos/db/testing` を import できるのは、テストのファイル(`*.test.ts`)と testing 自身だけにする。dependency-cruiser と ESLint の両方で検査し、違反の見本と通る見本のフィクスチャでテストする(F の追加)。
- テストごとに空の DB を作る(C)。テストは `pg` で SQL を直接書き、エラーのコードと制約の名前で拒否を確かめる(E)。取引を登録するテストは、合計0の仕訳を2行以上付けて同じ DB トランザクションで登録する(#47 の遅延制約が入っても書き換えずに済むように)。
- `apps/migrate` の結合テストの適用件数は、`_journal.json` の件数から求める(D)。
- `bigint` の列は `mode: "number"` にし、`postings.amount` に `-9007199254740991`〜`9007199254740991`、`accounts.unit_amount` に `1`〜`9007199254740991` の CHECK を付ける(G)。設計書 §3・§5.1 を直した。
- Red で「正しい操作が拒否されないこと」のテストが通るのは認め、Red の報告に失敗したテストと通ったテストを一覧で書く(H)。

## 結果
- 帳簿として壊れたデータ(金額0・存在しない勘定・決められていない種別など)は、アプリにバグがあっても DB が拒否する。これを結合テストで確かめられるようになった。
- 結合テストの DB は本番と同じ処理で作られるので、適用の仕方の違いによる見逃しがない。
- `@lifeos/db/testing` はテストのファイルからしか使えないので、本番のコードがテスト用の道具を経由してマイグレーションを適用することはない。
- テストごとに DB を作るので、テストの数に比例して結合テストの時間が延びる。遅くなったら、マイグレーションを適用した DB をひな型(`CREATE DATABASE ... TEMPLATE`)にする方法を検討する。
- `accounts.updated_at` を自動で更新するトリガーは、この Issue では作らない。
