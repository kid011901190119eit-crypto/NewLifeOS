# 0029: TDD の Red・Green・Refactor を別々のコミットにし、Red は型の合う仮の実装のうえで期待値の違いで失敗させる

- ステータス: 承認
- 日付: 2026-11-06

## 背景
ADR 0008 で TDD で進めると決めたが、本当にテストを先に書いたのか(Red → Green の順だったのか)を、あとから確かめる方法がなかった。実装役とレビュー役に分けて進める(ADR 0024)ようになり、レビュー役が順番を検査できる手がかりが欲しくなった(Issue #44)。

事情と制約は次のとおり。
- main へは Squash and merge でマージする(ADR 0020)ので、main には1つのコミットしか残らない。
- Vitest はテストの実行時に型を検査しない。型の誤りは `pnpm typecheck` でしか見つからない。
- Red のコミットを止める仕組み(Git のフック、CI など)はない。CI はプルリクエストの最新のコミットだけを検査する。

## 検討した選択肢
**順番の記録の仕方**
- Red・Green・Refactor を別々のコミットにする: コミットの履歴だけで順番を確かめられる。レビュー役がそれぞれのコミットを開いてテストを実行できる / コミットが増える。Red のコミットが先頭のまま push すると CI が落ちる
- プルリクエストの本文に「先にテストを書いた」と書くだけにする: 手間がない / 検査できない

**Red の失敗のさせ方**
- 型の合う仮の実装(ダミーの値を返す)を置き、期待値の違いで失敗させる: テストが「正しい値かどうか」を見分けられることを確かめられる / 仮の実装を書く手間がある
- ファイルや関数がない状態で失敗させる: 手間がない / 「見つからない」で落ちるだけなので、テストの期待値が効いているかがわからない
- `throw new Error("未実装")` で失敗させる: 書きやすい / 例外で落ちるので、期待値の違いによる失敗と見分けにくい。例外を投げることを確かめるテストでは、Red なのに通ってしまう

**Red のコミットの型チェック**
- `pnpm typecheck` が通ることも求める: Vitest では出ない型の誤りによる失敗も除ける / 確かめる手順が1つ増える
- 求めない: 手順が軽い / 型が合っていなくても見逃される

**対象の範囲**
- テストを書く変更だけに適用し、ドキュメントだけの変更は対象外にする: テストのない変更に意味のない Red を作らなくて済む / 範囲の判断が要る
- すべての変更に適用する: 例外がない / ドキュメントだけの変更では Red にあたるものがない

## 決定
- テストを書く変更では、Red と Green を別々のコミットにする。Refactor をした場合は、それも別のコミットにする。
- Red のコミットでは、型の合うダミーの値を返す仮の実装を置き、テストが期待値の違いで失敗する状態にする。例外で失敗させる仮の実装は使わない。Red のコミットで `pnpm typecheck` が通ることも確かめる。
- ドキュメントだけの変更は対象外にする。
- Red のコミットが先頭のまま push しない。
- レビュー役は、自分のワークツリーで Red と Green のコミットを読み取り用に開いてテストを実行し、Red では期待値の違いで失敗し、Green では通ることを確かめる。Red と Green の間でテストのファイルが変わっていないことも確かめる(AGENTS.md ルール2)。

## 結果
- TDD の順番と、テストの期待値が効いていることを、レビュー役がコミットの履歴から検査できるようになる。
- テストを通すためにテストを書き換えていないかも、Red と Green の差分で確かめられる。
- 分かれたコミットは作業ブランチとプルリクエストの上にだけ残り、main には1つのコミットとして入る。
- 実装役は、仮の実装を書いてからコミットする手間が増える。例外を投げることを確かめるテストでは、例外を投げない仮の実装を書く。
