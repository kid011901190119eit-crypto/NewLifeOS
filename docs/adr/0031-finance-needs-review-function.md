# 0031: 「要確認」の判定の関数の入力・並べ替え・結果の形

- ステータス: 承認
- 日付: 2026-11-06

## 背景
入力チェック(spec §3.3.1)に違反する取引を「要確認」と判定する処理を、`finance` の `domain` に純粋な関数として作る(Issue #48、`docs/design/finance-data-model.md` §6、ADR 0011)。判定のルールは決まっていたが、関数の入力と結果の形について3つの判断が必要だった。

## 検討した選択肢
**ルール1〜3の判定の入力**
- 画面入力の型(`TransactionInput`)を受け取る: 判定が「null かどうか」「同じ ID かどうか」だけで短い。種別ごとの型で誤った組み合わせを型チェックで防げる。未分類の勘定の ID を知らなくてよい / 保存済みの取引は、先に `fromPostings` で画面入力の形に戻す必要がある
- 保存された仕訳(種別+仕訳の行+未分類の勘定の ID)を受け取る: 設計書 §6 の書き方そのままで、開始残高も同じ関数に渡せる / 口座側・相手側を探す処理が `fromPostings` と二重になる。種別と仕訳が合わない組み合わせを型で防げない

**ルール4の累計残高の並べ替え**
- 関数の中で、取引日 → 登録日時 → 取引の ID の順に並べる: 呼ぶ側が並べ忘れても正しい結果になり、「同じ日の取引は登録順」をユニットテストで確かめられる / SQL の `ORDER BY` と同じことを二重に書く。入力に取引日と登録日時が要る
- 並んだ列を受け取る約束にする: 関数が短く、並べ替えが SQL の1か所になる / 並べ忘れると誤った結果を黙って返す。登録順のルールは結合テストまで確かめられない

**結果の形と関数の分け方**
- 判定の関数を2つ(ルール1〜3、ルール4)と、まとめる関数を1つ作る: ルールごとのテストが小さく書け、「複数のルールに違反するとすべて返る」をまとめる関数の1か所で確かめられる / 公開する関数が3つになる
- まとめる関数を1つだけ公開する: 入口が1つ / どのルールのテストにも、ほかのルールのデータが毎回要る
- ルールごとに4つの関数にし、まとめるのは呼ぶ側に任せる: 1つの関数が最も小さい / 「違反したルールがすべて返る」ことを domain で保証できない

## 決定
- ルール1〜3は**画面入力の型(`TransactionInput`)を受け取る**(`checkTransactionRules`)。保存済みの取引は `fromPostings` で戻してから判定する。理由: 種別ごとの型で間違いを防げ、仕訳から口座側・相手側を探す処理を `fromPostings` と二重に書かずに済むから。
- 開始残高は `TransactionInput` に含まれないので、ルール1〜3の関数には渡さず、その仕訳をルール4の入力にだけ入れる(ルール2の「開始残高にはラベルを求めない」は、この扱いで満たす)。
- ルール4は**関数の中で並べ替える**(`findUnitViolations`)。並べ替えは入力をコピーしてから行い、入力の配列を書き換えない。理由: 呼ぶ側が並べ忘れても正しい結果になり、登録順のルールをユニットテストで確かめられるから。
- 判定の関数を2つと、**まとめる関数 `detectNeedsReview`** を作る。結果は、要確認の取引だけを入れた `Map`(キーは取引の ID、値は違反したルールの配列)にする。ルールの名前は `transfer_destination`(ルール1)・`label_required`(ルール2)・`party_required`(ルール3)・`balance_unit`(ルール4)。理由: ルールごとのテストを小さく分けて書け、しかも「複数のルールに違反するとすべて返る」ことをまとめる関数の1か所でテストできるから。

前提として決めたこと:
- ルール4の入力は**有効な(取消されていない)取引の仕訳だけ**とする。取消済みを除くのは、`active_postings` から取り出す SQL(別の Issue)の仕事である。
- 管理単位は**1以上の整数**を前提とし、関数では検査しない。DB の CHECK 制約(管理単位は1以上)が守る。
- 同じ取引が同じ口座に2行の仕訳を持つとき(移動元=移動先)は、**その取引の仕訳を合計してから**累計残高を進める。移動先の口座や開始残高の口座の仕訳も、ルール4の入力に含める。
- 移動で2つの口座が同時に倍数でなくなっても、ルール4はその取引に1回だけ返す。

## 結果
- 判定の関数は `packages/modules/finance/src/domain/needs-review.ts` にあり、DB・HTTP・外部のライブラリを使わない。口座の ID・管理単位の型も domain の中で定義し、`src/db/schema.ts` に依存しない。
- 取引日は `"2026-11-06"` の形の文字列、登録日時は `Date` で受け取る。PostgreSQL の登録日時はマイクロ秒まであるが `Date` はミリ秒までなので、同じミリ秒の取引は取引の ID(UUIDv7 は時刻順)で並ぶ。
- `Map` は `JSON.stringify` で空(`{}`)になるので、フェーズ5で API から返すときは配列かオブジェクトに変換する必要がある。
