# 0013: 家計簿のテーブル設計の細部(ID・集計・取引の種別・開始残高)

- ステータス: 承認
- 日付: 2026-11-04

## 背景
家計簿のテーブル定義を確定するにあたり、主キーの型、残高の求め方、取引に入力時の種別を保存するか、開始残高の記録の仕方を決める必要があった。

## 検討した選択肢
**主キーの型**
- UUIDv7: 件数が推測できず、DBに問い合わせる前にIDを決められる。時刻順なのでインデックスが効率的 / 16バイトで長く、目で読みにくい
- bigint の連番: 小さく読みやすい / 登録するまでIDがわからない、件数が推測できる

**残高の求め方**
- 基準日を引数で渡す集計クエリ: テストで日付を固定でき、残高がずれない / 件数がとても多くなると遅い
- ビューの中で今日を求める: SELECTするだけで残高が出る / テストで今日を固定しにくい
- 残高テーブルを持つ: 読み取りが速い / 予定が日付の経過で確定になる処理が難しく、二重管理になる

**取引の種別**
- 列として保存する: 編集画面を再現でき、「貸す」「借りる」を区別できる / 仕訳との矛盾をアプリで防ぐ必要がある
- 仕訳から導出する: 二重管理がない / 「貸す」「借りる」や、未分類の取引の元の種別がわからない

**開始残高**
- 1つの取引にまとめる: 「1回だけ」をDBの部分UNIQUEで保証でき、開始日付が1つに決まる / 後から口座を足すときは開始残高ごと置き換える
- 口座・相手ごとに別の取引: 後から口座を足しやすい / 開始日付がばらばらになり、「1回だけ」の保証が複雑

## 決定
- 主キーは UUIDv7 にする。
- 残高・未精算額・月次集計は、毎回仕訳から集計する。「今日」はアプリが Asia/Tokyo で求め、引数で渡す。残高テーブルは持たない。
- 取引に種別(`regular` / `transfer` / `lend` / `borrow` / `opening`)を保存する。仕訳には「口座側か相手側か」(`role`)を保存する。
- 開始残高は1つの取引にまとめ、取消されていない開始残高は1件だけとする(部分UNIQUEインデックス)。

## 結果
- PostgreSQL 18 未満を使う場合は、UUIDv7 をアプリで生成する。
- 件数が増えて集計が遅くなったら、インデックスの追加から検討する(残高テーブルは、そのとき改めて判断する)。
- 種別・役割と仕訳の組み合わせが正しいことは、アプリの変換関数とユニットテストで守る。
