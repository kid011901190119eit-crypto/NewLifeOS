# 0024: 指揮役・実装役・レビュー役に分け、Orca のオーケストレーションで Issue を半自動で進める

- ステータス: 承認
- 日付: 2026-11-04

## 背景
Issue #27 で、オーナーが「やりたいこと」を伝えるだけで、Issue の作成からプルリクエストとレビュー結果の報告までを進められる仕組みを作ることにした。それまでは、1つのセッションで `/issue <番号>` の手順(ADR 0023)を使い、レビューも同じセッションが行っていた。

事情と制約は次のとおり。
- オーナーが話す相手は1人(指揮役)にしたい。判断の分かれ目は、これまでどおりオーナーが選ぶ(AGENTS.md ルール9)。
- レビューは、実装に引きずられないように、実装を見る前に合格の条件を決めたい。
- Claude Pro の利用枠に限りがある。
- Orca のオーケストレーションは実験的な機能で、コマンドが変わることがある(確かめたのは 1.4.247)。

## 検討した選択肢
**役割の手順を書く場所**
- AGENTS.md には要約と守ることだけを書き、詳細は `docs/agents/*.md` に分ける: AGENTS.md はすべてのセッションが毎回読むので、短いほど利用枠を節約できる / 読むファイルが増える
- AGENTS.md に全部書く: 1か所で済む / すべてのセッションで、関係のない長い手順を毎回読む

**レビュー役の待たせ方**
- 同時に起動し、チェックリストを作ったら `worker_done` で止める。実装が終わったら同じレビュー役に `send` で段階2を渡す: 待っている間は利用枠を使わない。チェックリストを作った理由を覚えたまま検査できる / 会話が長くなり、段階2の1回あたりの消費が少し増える
- 段階2では新しいレビュー役を起動し、チェックリストを渡す(Task の依存関係で待たせる): 文脈が軽い / 起動のコストがかかる。作った経緯を引き継げない

**レビューの時期**
- push の前に手元のブランチをレビューし、レビューコメントは最後にまとめて付ける: push の確認と CI の実行が1回で済む / 途中の経過は GitHub に残らず、最後のコメントにまとめる必要がある
- 先に push してプルリクエストの上でレビューする: 経過がすべて GitHub に残る / 修正のたびに push と CI が走り、push の確認も増える

**指摘と修正の往復の上限**: 2回 / 3回 / 上限なし(利用枠を使い切るおそれがある)

**モデル**: 指定しない(全員が既定のモデルを使う) / 指揮役とレビュー役の段階1を軽いモデルにする(節約になるが、確認の質が落ちるかもしれない)

## 決定
- 役割の手順は `docs/agents/coordinator.md`・`implementer.md`・`reviewer.md` に書き、AGENTS.md には要約・共通して守ること・手で戻る方法・片付けを書く。
- 指揮役は `/start <やりたいこと>`(`.claude/commands/start.md`)で始める。レビュー役を手で始めるために `/review-issue`(`.claude/commands/review-issue.md`)も用意する。Claude Code に組み込みの `/review` と名前がぶつからないように、この名前にした。
- 実装役とレビュー役は、`worker-start --worktree new-child` で、それぞれの子ワークツリーに同時に起動する。
- レビュー役は段階1のあと止まり、指揮役が `send` で段階2を渡す。
- レビューは push の前に行う。チェックリストと指摘の経過は、最後に `gh pr review --comment` でプルリクエストに残す。
- 往復は2回まで。モデルは指定しない。
- レビュー役のわざと壊す実験は、自分のワークツリーで `git switch --detach` で開いた実装役のブランチの上でだけ行う。終わったら元に戻し、コミットと push は一切しない。

## 結果
- オーナーは指揮役とだけ話せばよくなる。レビューの基準が実装より先に決まる。
- 待っている作業役は利用枠を使わない。ただし、指揮役やレビュー役の会話が長くなると、1回あたりの消費は増える。
- 同じアカウントで作ったプルリクエストには「承認」ができないので、レビューの結果はコメントとして残る。
- 実験的な機能に頼るので、コマンドが変わると手順書が古くなる。指揮役は始める前に最新の説明を確かめる。動かないときは、`/issue` と `/review-issue` で手に戻せる。
- 実際の運用は、フェーズ3-2(packages/db と Testcontainers による結合テスト)の Issue が最初になる。その結果をもとに、手順と、この ADR を見直す。

## 追記(2026-11-05)
- マージのあとの片付け(作業役を閉じる・子ワークツリーとブランチを消す)は、指揮役の手順から外し、オーナーが手で行うことにした。AGENTS.md と `docs/agents/coordinator.md` から該当の項目を削除した。
