# 0028: 画面入力と仕訳の変換関数の型(入力の形・金額・システム勘定・拒否・逆変換)と、domain のテストの依存

- ステータス: 承認
- 日付: 2026-11-05

## 背景
フェーズ4の最初の作業として、画面入力を仕訳に変換する処理と、その逆の処理を `finance` の `domain` に純粋な関数として作る(Issue #42、`docs/design/finance-data-model.md` §4、ADR 0010)。変換の公式は決まっていたが、関数の入出力の型について5つの判断が必要だった。

また、domain に初めてファイルを置いたところ、隣に置いたテストが Vitest を import することが、境界の検査(「domain が使ってよい外部のライブラリは Zod だけ」。`docs/design/module-system.md` §5.2)の違反になった。

## 検討した選択肢
**入力の型の形**
- 種別ごとに分けた型のユニオン(判別可能なユニオン型): 画面の項目名(ラベル・移動先・相手)が型に出て、誤った組み合わせを型チェックで防げる / 型の数が増え、新しい概念を学ぶ必要がある
- 1つの平らな型(`counterAccountId` で相手側をまとめる): 型が1つで単純 / 相手側が何かが型から読めず、組み合わせの誤りを防げない

**金額の型**
- 安全な整数だけを扱う `number`: JSON・Zod でそのまま扱え、§4.4 の `Number.isSafeInteger` の前提と合う / 型の上では小数も入れられる
- `bigint`: DB の列と同じで、小数が型として入らない / JSON に書けず、`number` と混ぜると型エラーになるなど扱いが面倒

**「未分類」「開始残高」の勘定の渡し方**
- 引数で ID を渡す: domain が DB を知らないまま本物の ID を入れた仕訳を返せる / 呼ぶたびに ID を用意する
- 仕訳に目印を入れ、保存する層で ID に置き換える: 引数が少ない / 仕訳の型が2種類になり、保存の層の仕事が増える
- ID をコードの定数にする: 引数が要らない / DB とコードの二重管理になり、マイグレーションも変える必要がある

**開始残高の拒否(仕訳が2行未満・同じ勘定が2回)の表し方**
- 結果の型(`{ ok: true, postings } | { ok: false, error }`): 拒否されうることが型に出て、受け止め忘れを型チェックで防げる / 呼ぶ側で毎回 `ok` を確かめる
- 例外(throw): 書き方が短い / 型を見ても例外が出るかわからず、処理忘れに気づきにくい

**逆変換で口座側を見分ける方法**
- 仕訳に `role`(`account` / `counter`)を持たせる: 移動元=移動先でも区別でき、DB の `postings.role`(§3.3)と同じ / 仕訳の項目が1つ増える
- 仕訳の並び順で見分ける: 項目が増えない / DB から読む順番に依存して壊れやすい

**domain のテストが Vitest を使えない問題**
- domain のテストファイル(`*.test.ts`)だけ Vitest の import を許す: テストを本体の隣に置く今の慣習のままにできる。テストはビルドに含まれないので本体の純粋さは変わらない / 共通の検査ルールを変える
- テストを domain の外に置く: 検査ルールを変えなくてよい / 今の慣習と違い、tsconfig の include と ESLint の対象も変える必要がある
- Vitest の globals 設定で import をなくす: 検査ルールを変えなくてよい / どこから来たかわからない関数が使えるようになり、AGENTS.md ルール8(ブラックボックスにしない)に反する

## 決定
- 入力は**種別ごとの型の判別可能なユニオン**にする(`regular` / `transfer` / `lend`・`borrow`)。開始残高は形が違うので別の型・別の関数にする。理由: 移動にラベルのような誤った組み合わせを、動かす前に型チェックで防げるから。
- 金額は**安全な整数だけを扱う `number`**(円)にする。DB の列は `bigint` のまま。整数かどうかの検査は §4.4 の入力の拒否(別の Issue)で、変換の前(operations)に入れる。理由: JSON でそのまま扱え、安全な整数だけを受け付ければ AGENTS.md ルール15の目的(誤差を出さない)は守れるから。
- 未分類・開始残高の勘定は**引数で ID を渡す**(`{ uncategorizedId, openingBalanceId }`)。理由: domain は DB を知らないままにし、テストでは架空の ID を渡せるから。
- 開始残高の拒否は**結果の型**で表す。理由: 受け止め忘れを型チェックで防げ、普通に起こりうる入力の間違いをプログラムの誤りと区別できるから。保存済みの仕訳の形が壊れていて逆変換できない場合は、プログラムかデータの誤りなので例外にする。
- 逆変換は**仕訳の `role` で口座側と相手側を見分ける**。相手側が未分類の勘定なら「なし」として復元する。対象は開始残高以外の4種別だけにする(開始残高の編集のしかたはフェーズ5の画面設計で決める)。

- domain の**テストファイル(`*.test.ts`)だけ、Vitest の import を許す**。テストでも DB と、Zod・Vitest 以外の外部のライブラリは禁止のまま。domain の本体は今までどおり Zod だけ。ESLint の境界ルールと dependency-cruiser の両方を同じ内容にする。理由: Vitest はテストをするための道具なので、テストから使うのはよいから。

## 結果
- 変換関数は `packages/modules/finance/src/domain/posting-conversion.ts` にあり、DB・HTTP・外部のライブラリを使わない。
- DB に保存する層(別の Issue)で、`number` と `bigint` の変換と、システム勘定の ID の取得(`system_key` から引く)が必要になる。
- AGENTS.md ルール15とロードマップのフェーズ4の完了の条件の文言を、「DB は `bigint`、TypeScript では安全な整数の `number`」とわかる形に直した。
- `packages/config/eslint-boundaries.js` は domain のテストファイルにだけ別のポリシーを当て、`dependency-cruiser.base.js` は `domain-only-zod`(本体)と `domain-test-only-zod-and-vitest`(テスト)の2つのルールに分けた。`packages/config/tests` の境界のテストで、両方の向き(テストは使える・本体は使えない)を確かめている。
- 学習ノート: [`docs/learning/discriminated-union.md`](../learning/discriminated-union.md)
