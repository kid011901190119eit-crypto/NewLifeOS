# 0011: 入力チェックに違反する取引も保存し、「要確認」は導出する

- ステータス: 承認
- 日付: 2026-11-04

## 背景
spec FIN-08 は、入力チェック(§3.3.1)に違反する取引を「要確認」として扱うとしている。しかし複式簿記では、ラベル・相手・移動先がないと仕訳の相手側の勘定が決まらず、合計0の仕訳を作れない。また、ルール4(口座の残高が管理単位の倍数)を、どの取引の問題として示すかも決める必要があった。

## 検討した選択肢
**違反のある取引の保存**
- 保存する(相手側を「未分類」勘定にする): FIN-08 と Notion版の操作感に合い、エージェントの不完全な入力も後で直せる / 「未分類」という特別な勘定が増える
- ルール1〜3は拒否し、ルール4だけ要確認: データが常にきれいで、DBで強く守れる / FIN-08 の書き換えが必要、不完全な入力は登録できない

**ルール4の判定単位**
- その残高にした取引: どの入力がおかしいかわかる / 同じ日の取引の順番を決める必要がある
- 口座を要確認にする: 計算が単純 / 原因の取引を自分で探す必要がある

## 決定
- 違反のある取引も保存する。ラベル・相手・移動先がないときは、仕訳の相手側をシステム勘定「未分類」(`suspense`)にする。移動元と移動先が同じ移動もそのまま保存する。
- 「要確認」は状態として保存せず、毎回導出する。4つのルールはすべてアプリ(TypeScriptの純粋関数)で判定する。
- ルール4は、口座ごとの累計残高(日付、登録順の順)が**管理単位の倍数でなくなった取引**を要確認にする。予定の取引も含める。
- 「移動先がない移動」はルール1の違反として扱う。

## 結果
- 入力チェックのルールはDBの制約にしない(制約にすると保存が拒否されるため)。DBは仕訳合計0などの構造のルールだけを守る。
- 「未分類」の残高が0でなければ、どこかに要確認の取引が残っているとわかる。月次集計にも未分類を含める。
- 同じ取引に同じ勘定の仕訳が2行あることを許す(UNIQUE制約を付けない)。
- 同じ日の取引の順番は登録順になり、編集するとその日の最後に移る。
