# 0016: 処理は「操作」として共通にし、RESTのルートとMCPのツールは別々の薄い入口として書く

- ステータス: 承認
- 日付: 2026-11-04

## 背景
LifeOS は、すべての操作を画面(REST API)からもエージェント(MCP ツール)からも行える(spec §1.2、CORE-03)。そのため、同じ処理(例: 取引の登録)を REST と MCP の2つの入口に出す必要がある。処理の本体と入口をどう分けて定義するかを決める必要があった。

## 検討した選択肢
- 処理は共通にし、入口は別々に書く: モジュールは「操作」(Zod の入力スキーマと関数)を1つ書き、REST のルートと MCP のツールはそれを呼ぶ薄い入口として手で書く。特別な仕組みがなく、エージェント向けの説明文や引数を画面向けと変えられる / 入口のコードが少し重複する
- 1つの定義から両方を自動で作る(`defineOperation` からコアが REST と MCP を生成): 重複がなく、両者がずれない / コアの仕組みが大きくなり、REST と MCP で振る舞いを変えたい場合に例外の扱いが必要になる

## 決定
- モジュールの処理の本体は `src/operations/` に「操作」として書く。操作は Zod の入力スキーマと、`(ctx: ModuleContext, call: CallContext, input)` を受け取る関数の組である。
- REST のルート(`src/server/routes.ts`)と MCP のツール(`src/server/tools.ts`)は、入力を検証して操作を呼ぶだけの薄い入口として、それぞれ手で書く。
- 作成元(`user` / `agent`)と冪等キーは、入口が `CallContext` に詰めて操作に渡す。REST は `Idempotency-Key` ヘッダー、MCP は入力の `idempotency_key` を使う。書き込みツールの入力に `idempotency_key` があることは、コアが起動時に検査する。
- 詳細は [`docs/design/module-system.md`](../design/module-system.md) を正とする。

## 結果
- 業務のルール(仕訳の変換、入力チェック、冪等キー、変更履歴、outbox)は操作の中にだけ書かれるので、REST と MCP で結果が食い違わない。
- 入口が薄いので、テストの中心は操作のテストになり、入口のテストは「正しく操作を呼んでいるか」の確認で済む。
- ツールの説明文はエージェント向けに、REST のパスとステータスコードは画面向けに、それぞれ最適な形で書ける。
- REST のルートと MCP のツールの数がそろっているか(片方だけにある操作がないか)は自動では保証されない。必要になったら、アーキテクチャテストで確かめることを検討する。
