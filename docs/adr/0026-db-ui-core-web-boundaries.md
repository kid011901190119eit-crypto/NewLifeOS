# 0026: db・ui はいちばん下の層にし、コアのサーバー側と core/web はお互いを import しない

- ステータス: 承認
- 日付: 2026-11-05

## 背景
#8 で境界の検査を入れたとき、`docs/design/module-system.md` §5.2 の表に書かれていない組み合わせが残った(#9 のコメント)。ESLint(eslint-plugin-boundaries)は「許可したもの以外はすべて禁止」、dependency-cruiser は「表の行ごとに、許可する行き先以外を禁止」で書いているため、表に行がないものは2つの道具で結果が食い違っていた。

- `packages/db`・`packages/ui` からの import: ESLint では禁止、dependency-cruiser では検査していない
- コアのサーバー側から `core/web` への import: ESLint では禁止、dependency-cruiser では許可

`core/web` から db・コアのサーバー側への import は、#12 で両方の道具で禁止済みである(ADR 0018)。

## 検討した選択肢
**db・ui が import してよいもの**
- 外部のライブラリと自分の中だけ: いちばん下の層になり、依存が一方向にそろう。ESLint の今の結果を変えなくてよい / db が core の型などを使いたくなったら、ルールを変える必要がある
- ワークスペースの中も許可する: 柔軟 / ui からサーバー側のコードを import でき、ブラウザに入るおそれがある。db → core → db のような循環は `no-circular` でしか止まらない
- 今は決めない: 実物を見てから決められる / 食い違いが残り、ui を作るときに忘れるおそれがある

**コアのサーバー側から core/web への import**
- 禁止する: 両方向とも禁止になり、ルールが単純で対称になる / サーバーと画面の両方で使う型は、core の外の別の場所に置く必要がある
- 許可する: サーバー側で画面用の型を使える / 向きによって扱いが違い、覚えにくい
- 型だけ許可する: 実行するコードは混ざらず、型は共有できる / ルールが1つ増え、少し複雑になる

## 決定
- db・ui が import してよいのは、外部のライブラリと自分のパッケージの中だけにする。
- コアのサーバー側から `core/web` への import は、型だけでも禁止する。
- dependency-cruiser に `db-deps`・`ui-deps` を足し、`core-deps` の行き先から `core/web` を外す。ESLint は、もともとこの結果になっているので変えない。
- 開発用の設定の共有(`packages/config`)は、これまでどおり表の対象外にする。

## 結果
- §5.2 の表のすべての要素に行ができ、2つの道具の結果がそろった。どちらもフィクスチャのテストで確かめている。
- サーバーと画面の両方で使う型の置き場所は、core の中にはない。必要になったときに、置き場所を決める。
- db が core の型などを使いたくなったら、この ADR を置き換えてからルールを変える。
