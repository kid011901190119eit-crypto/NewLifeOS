# 0015: モジュール間の連携は公開用の入口とZodで定義したイベントで行い、境界を3つの仕組みで検査する

- ステータス: 承認
- 日付: 2026-11-04

## 背景
spec §4.2 では、他のモジュールのテーブルを直接読み書きせず、イベントか公開されたインターフェースで連携すると決めている。しかし、公開インターフェースの受け取り方、イベントの中身の型の決め方、ルールが破られたときに気づく仕組みは決まっていなかった。また、変更履歴(CORE-04)はコアの機能だが、取り消しにはモジュールのデータの書き換えが必要になる。

## 検討した選択肢
**公開インターフェースの受け取り方**
- 公開用の入口(`@lifeos/<id>/public`)を直接 import する: 普通の関数呼び出しなので、型も定義元へのジャンプも効き、仕組みが明快 / モジュール同士がコードの上で直接つながる
- コア経由で受け取る(マニフェストに提供するもの・必要なものを宣言し、実行時に `ctx.modules.get()` で受け取る): 依存関係がマニフェストに明示され、テストで偽物に差し替えやすい / 間接的になる分、理解が少し難しい

**イベントの中身の型**
- Zod のスキーマ+版番号: 発行時・受信時に実行中の検証ができ、outbox に残った古い形のイベントも検出できる / スキーマを書く手間が増える
- TypeScript の型だけ: 簡単 / DB から読んだ中身が型どおりである保証がない

**境界違反を防ぐ仕組み**(複数選択)
- package.json の `exports`: 公開用の入口以外を解決できなくする。費用はほぼゼロ
- ESLint の境界ルール(eslint-plugin-boundaries): 依存の向きのルールをファイルの種類ごとに検査する。エディタで気づける
- アーキテクチャテスト(dependency-cruiser と Vitest): 依存のグラフ全体(循環を含む)と、ESLint では見えない約束(SQL、スキーマ、一覧の一致)を検査する
- DB のロールをモジュールごとに分ける: 最も強いが、モジュールごとに DB 接続が必要になり、仕様にない構成要素が増える

## 決定
- 同期の読み取りは、相手のモジュールの公開用の入口を直接 import して行う。公開用の入口は MVP では**読み取り専用**とする。書き込みを公開すると、変更履歴・作成元・冪等キーの責任があいまいになるため。
- 非同期の連携はイベントで行う。イベントは `defineEvent`(名前・版番号・Zod スキーマ)で定義して公開用の入口から出し、発行時と受信時に検証する。中身の形を変えたら版番号を上げる。受け手は、受け取るイベントの名前と版番号を宣言する。
- 受け手の冪等性は、コアの `core.processed_events` に(受け手の完全名、イベントID)を記録し、受け手の処理と同じトランザクションでコミットすることで保証する。
- 変更履歴はコアが `core.changes` に記録する。取り消しは、モジュールがマニフェストの `changeHandlers` に登録した関数をコアが呼んで行う。コアはモジュールのテーブルを直接書き換えない。
- 境界の検査には、package.json の `exports`、ESLint の境界ルール、アーキテクチャテストの3つを使う。DB のロールの分離は採用しない。
- 詳細は [`docs/design/module-system.md`](../design/module-system.md) を正とする。

## 結果
- 境界違反に、型チェック・エディタ・CI の3段階で気づける。それぞれが見逃すものを、他の仕組みが補う。
- eslint-plugin-boundaries と dependency-cruiser を、フェーズ2以降の実装時に依存関係として追加する(追加の時点でオーナーに確認する)。
- 他のモジュールのデータを書き換えたい要件が出てきたら、公開用の入口に書き込みを足す前に、改めて設計を検討してADRに残す。
- DB の権限による防御はないので、生の SQL で他のスキーマを触るコードは、アーキテクチャテストの文字列検査に頼る。すり抜けが見つかったら、DB のロールの分離を改めて検討する。
