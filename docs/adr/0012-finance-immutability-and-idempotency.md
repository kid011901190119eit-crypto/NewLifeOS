# 0012: 取引は取消フラグと置き換えで変更し、冪等キーは専用テーブルで管理する

- ステータス: 承認
- 日付: 2026-11-04

## 背景
spec §5.1 で物理削除をしないと決めているが、FIN-01 では取引の編集・削除ができる必要がある。また、書き込みAPIは冪等キーを受け取り、エージェントの再送で二重登録しないようにする必要がある。同じキーで内容の違うリクエストが来たときの動きは決まっていなかった。

## 検討した選択肢
**編集・削除の表し方**
- 取消フラグ+置き換え: 一覧がすっきりし、置き換えの履歴も追える / すべての集計で取消の除外が必要
- 打ち消しの取引: 会計ソフトの正式なやり方 / 一覧に打ち消しが並び、操作感が変わる
- 仕訳の UPDATE を許可し、過去の値はコアの変更履歴に任せる: 実装が簡単 / 家計簿のテーブルだけでは過去の姿がわからない

**同じ冪等キーで内容が違うとき**
- エラー(409)にする: キーの使い回しミスに気づける / ハッシュの列と比較処理が増える
- 内容に関わらず最初の結果を返す: 単純 / 新しい取引が黙って捨てられる

## 決定
- 削除は取引の `voided_at` を設定する(取消)。編集は、元の取引を取消して `replaces_id` で元を指す新しい取引を作る(置き換え)。
- 仕訳は一度書いたら変えない。取引は取消の設定以外で変えない。取消の解除もしない。DBのトリガーで UPDATE・DELETE・TRUNCATE を制限する。
- 変更履歴(CORE-04)からの取り消しも、新しい取引を足すことで表す。
- 冪等キーは `finance.idempotency_keys` テーブルで管理し、リクエスト内容のSHA-256を一緒に保存する。同じキー・同じ内容なら最初の結果を返し、内容が違えば 409 エラーにする。
- spec §5.4 案の `transactions.idempotency_key` 列は、専用テーブルに置き換える(取消のように新しい取引を作らない操作にも冪等キーが要るため)。

## 結果
- すべての過去の記録がDBに残り、「いつ・誰が(user / agent)・何を変えたか」を家計簿のテーブルだけで追える。
- 集計で取消の除外を忘れないよう、有効な仕訳だけを見せるビュー(`active_postings`)を用意し、集計はすべてそれを使う。
- 編集のたびに行が増えるが、個人用の件数では問題にならない。
