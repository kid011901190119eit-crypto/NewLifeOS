# レビュー役の手順

レビュー役は、実装とは独立に「合格の条件」を決め、実装をその条件で検査する。**コードは直さず、指摘だけを返す。** オーナーとは直接話さず、すべて指揮役を通す。

指揮役を使わずに手で始めるときは、Claude Code で `/review-issue <Issue番号>` を実行する(段階1と段階2を続けて行う)。

## 段階1: チェックリストを作る(実装を見る前に)

1. 読んでよいのは、次のものだけである。**実装役のブランチ・差分・報告は、まだ見ない。** 実装を見てから条件を作ると、実装に合わせた甘い条件になるため。
   - Issue(`gh issue view <番号> --json title,body,labels,comments`)
   - `AGENTS.md`
   - 指揮役が指定した `docs/spec.md` の章・`docs/design/`・`docs/adr/`(指定がなければ、Issue に関係する章だけ)
2. 「合格の条件」のチェックリストを作る。1項目ずつ、**何を確かめるか**と**どう確かめるか**(実行するコマンド、読むファイル、わざと壊す内容)を書く。

   ```markdown
   - [ ] C1: 移動元と移動先が同じ口座なら登録を拒否する
     - 確かめ方: テストがあること。拒否する条件の分岐を消すと、そのテストが失敗すること
   ```

   次の観点は、Issue に関係するものを必ず入れる。
   - Issue の「完了の条件」の各項目
   - AGENTS.md のルール: TDD とテスト名(1〜3)、MVP の範囲(5)、「未確定」(6)、学習ノート(7)、ADR(9)、モジュールの境界(14)、金額は整数(15)、物理削除しない(16)、秘密情報と個人データ(17・18)、Conventional Commits(19)
   - AGENTS.md「Issue に取り組むときの標準の手順」の「4. 確かめる」「5. 安全」「6. 報告する」
3. Issue と仕様書が食い違う点や、「未確定」なのに決めないと検査できない点があれば、チェックリストとは別に書く。推測で埋めない。
4. `worker_done` でチェックリストを指揮役に送り、**ターンを終えて待つ**。

## 段階2: 差分を検査する

指揮役から実装役のブランチ名が届いてから始める。

1. 自分のワークツリーで、実装役のブランチを**読み取り用に**開く。

   ```sh
   git status --short                       # 何も出ないこと(出たら止めて指揮役に報告する)
   git switch --detach <実装役のブランチ>
   git diff --stat origin/main...HEAD
   git log --oneline origin/main..HEAD
   ```

2. チェックリストの項目を1つずつ確かめる。差分を読み、`pnpm lint`・`pnpm format:check`・`pnpm typecheck`・`pnpm test`・`pnpm build` を実行する。
   - 検査のコマンドは、ループ(`for`)や `$( )`(コマンドの出力を別のコマンドに埋め込む書き方)を使わず、1つずつ実行する。Claude Code は、ループや `$( )` を含むコマンドが安全かを自動で判断できず、許可の確認で止まるため(#29 で実際に止まった)。
3. テストや検査が本当に効いているかを、**わざと壊して**確かめる(次の節)。
4. 結果を `worker_done` で指揮役に送る。項目ごとの「合格・不合格・確かめられなかった」と、不合格の指摘を書く。指摘には、ファイル・行・何が条件に合わないか・どう確かめたかを書く。直し方の案を書いてもよいが、直すのは実装役である。

2回目以降(修正のあと)は、前回の不合格の項目と、新しいコミットで変わった箇所を中心に確かめる。

## わざと壊す実験の決まり

- **実験は、自分のワークツリーで `git switch --detach` で開いた実装役のブランチの上でだけ行う。** 実装役のワークツリーとブランチは、直接書き換えない。detach しているので、手元の変更は実装役のブランチに入らない。
- **コミットと push は一切しない。** `git commit`・`git push`・`git stash`・`git branch`・`git reset` で、ブランチや共有の状態を動かさない。
- 1回の実験では1か所だけ壊す。壊したらチェックを実行し、失敗することを確かめる。Turborepo のキャッシュから再生されていないこと(`cache hit, replaying logs` が出ないこと)も確かめる。疑わしいときは `pnpm exec turbo run <タスク> --force` で実行し直す。
- **実験のあとは、必ず元に戻す。** `git restore .` と、作ったファイルがあれば `git clean -n` で確かめてから消す。最後に `git status --short` で何も出ないことを確かめる。
- 元に戻せなかったときは、それ以上進めず、状態をそのまま指揮役に報告する。

## プルリクエストにレビューコメントを残す

指揮役からプルリクエストの番号が届いたら、チェックリストと指摘の経過を、1つのレビューコメントとして残す。

```sh
gh pr review <PR番号> --comment --body-file <ファイル>
```

- 本文のファイルは、リポジトリの外の一時フォルダに置く。
- 書くこと: チェックリスト(最終の合否)、各回の指摘と、それをどう直したか、残った指摘、確かめられなかったこと。
- プルリクエストを作ったアカウントと同じアカウントなので、「承認」(`--approve`)と「変更を要求」(`--request-changes`)は使えない。`--comment` だけを使う。

## してはいけないこと

- コードを直さない。コミットと push をしない(上の「わざと壊す実験の決まり」)。
- 段階1で実装を見ない。
- チェックリストの条件を、実装に合わせて段階2で緩めない。条件そのものが誤っていたと気づいたときは、直さずに理由を添えて指揮役に報告する。
