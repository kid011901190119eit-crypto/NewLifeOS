# 実装役の手順

実装役は、指揮役から Issue を受け取り、[`AGENTS.md`「Issue に取り組むときの標準の手順」](../../AGENTS.md#issue-に取り組むときの標準の手順)で作業する。オーナーとは直接話さない。**オーナーに確認するべきことは、すべて指揮役を通す。**

標準の手順との違いは、次の3点だけである。

## 1. 計画の確認は `ask` で行う

「2. 計画する」で作った計画(作る・変えるファイルの一覧、判断が分かれる点と選択肢ごとの利点・欠点、MVP の範囲外や「未確定」に触れる点)を、`ask` で指揮役に送る。

```sh
xargs -0 -a <計画を書いたファイル> orca orchestration ask --from <自分の handle> --question
```

- 計画は長く、引用符や `` ` `` を含むので、リポジトリの外の一時フォルダのファイルに書いてから渡す。`--from` には、依頼の冒頭(preamble)にある自分の handle を書く。
- `ask` にはファイルから質問を読むオプションがない(Orca 1.4.247)。`$( )` で埋め込むと Claude Code の許可の確認で止まることがあるので、`xargs` でファイルの中身を `--question` に渡す(学習ノート参照)。
- この方法も許可の確認で止まるときは、計画のファイルの絶対パスだけを `--question` に書いて送り、指揮役にファイルを読んでもらう。
- 選択肢が1つの問いに絞れるときは、`--options "<選択肢1>,<選択肢2>"` を付けてもよい。

- 送ったら、**ターンを終えて待つ**。回答が届くと Orca が起こしてくれる。待っている間に書き始めない。
- 作業の途中で判断が分かれたとき、仕様と食い違うテストを見つけたとき(ルール2)も、同じように `ask` で聞く。
- 指揮役はオーナーに中身をそのまま見せるので、選択肢・利点・欠点を省かずに書く。オーナーは開発経験が浅いので、専門用語には短い説明を添える。

## 2. push の前で止まって報告する

「4. 確かめる」まで済んだら、push せずに `worker_done` で報告する(コミットは作業ブランチにしておく)。

- 報告に書くこと: ブランチ名、最後のコミットの SHA、変えたファイルの一覧、`pnpm lint`・`format:check`・`typecheck`・`test`・`build` の結果、AGENTS.md「6. 報告する」の3つ
- この報告をもとに、レビュー役がブランチを読む。報告のあとは、指揮役から次の指示が届くまでブランチを動かさない。

## 3. 指揮役の指示で続きを行う

### 指摘を受けたとき

- 指摘ごとに、直すか、直さない理由を返すかを決める。指摘に納得できないときは、直さずに理由を書いて返す。指揮役がオーナーに判断を仰ぐ。
- テストを書き換えて指摘を消してはいけない(ルール2)。
- 直したら「4. 確かめる」をやり直し、2と同じ形で報告する。どの指摘をどのコミットで直したかを書く。

### push の承認を受けたとき

標準の手順の「7. 仕上げる」を行う。push し、プルリクエストを作り、`gh pr checks <番号> --watch` を実行する。プルリクエストの番号と CI の結果を `worker_done` で報告する。

## してはいけないこと

- 指揮役からの承認なしに push しない。マージはしない。
- オーナーに直接質問しようとしない(ターミナルに質問を書いて待つのではなく、`ask` を使う)。
- レビュー役のワークツリーに触らない。
