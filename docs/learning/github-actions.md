# GitHub Actions(CI の自動実行)

## それは何か

**GitHub Actions** は、GitHub の上で、プッシュやプルリクエストなどの出来事をきっかけに、決めておいた処理を自動で実行する仕組みである。**CI**(継続的インテグレーション)は、変更のたびに Lint・テスト・ビルドなどを自動で実行し、壊れた変更を早く見つける習慣のこと。このプロジェクトでは、GitHub Actions で CI を動かす。

| 用語 | 意味 |
|---|---|
| ワークフロー | 自動で実行する処理のまとまり。`.github/workflows/*.yml` に1ファイルずつ書く |
| トリガー(`on`) | ワークフローを始めるきっかけ。`pull_request`(プルリクエストの作成・更新)や `push` など |
| ジョブ(`jobs`) | ワークフローの中の実行単位。ジョブごとに新しいランナーが用意され、ジョブ同士は並列に動く |
| ステップ(`steps`) | ジョブの中で上から順に実行する処理。コマンド(`run`)か、アクション(`uses`)を書く |
| アクション | よく使う処理を部品にしたもの。`actions/checkout`(リポジトリの取り出し)など、他のリポジトリで公開されている |
| ランナー(`runs-on`) | ジョブを実行する仮想マシン。GitHub が用意したもの(`ubuntu-24.04` など)を使う。実行が終わると捨てられる |
| マトリックス(`strategy.matrix`) | 1つのジョブの定義から、値を変えた複数のジョブを作る仕組み |
| キャッシュ | ランナーは毎回まっさらなので、前回ダウンロードしたものを GitHub に保存しておき、次の実行で復元して時間を短くする |
| 権限(`permissions`) | ワークフローに渡される一時的なトークン(`GITHUB_TOKEN`)が、リポジトリに対して何をしてよいか |

## なぜ必要か

- ローカルで `pnpm test` などを実行するのを忘れても、プルリクエストの画面で失敗に気づける。
- 「品質チェックを通らないものは main に入らない」(ロードマップのフェーズ2の目的)を、人の注意ではなく仕組みで守る。CI のジョブを、main のルールセットの**必須チェック**にすると、失敗したプルリクエストはマージできなくなる。
- ランナーは毎回まっさらな環境なので、「自分のパソコンでだけ動く」状態(入れ忘れた依存関係、コミットし忘れたファイルなど)を見つけられる。

## このプロジェクトでどう使うか

ワークフローは [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) にある。

### トリガー

- `pull_request`: プルリクエストを作ったときと、そのブランチにプッシュしたとき。
- `push`(`main` のみ): マージ後の main でも、同じチェックが通ることを確かめる。

### ジョブ:5つに分ける

`lint`・`format`・`typecheck`・`test`・`build` の5つのジョブに分けている(オーナーが選んだ構成)。

- 利点: プルリクエストの画面で、どのチェックが失敗したかが一目でわかる。必須チェックを1つずつ指定でき、並列に動く。
- 欠点: ジョブごとにランナーが別なので、依存関係のインストールと、依存先のパッケージのビルド(`^build`)を、それぞれのジョブでやり直す。

5つのジョブは手順が同じで、最後のコマンドだけが違う。そのため、マトリックスで1つの定義から5つのジョブを作っている。`name: ${{ matrix.task }}` により、ジョブの名前は `lint`・`format` などになる。この名前が必須チェックの名前になるので、変えるときはルールセットの設定も直す。`fail-fast: false` は、1つが失敗しても残りのジョブを止めない設定である(全部の結果を一度に見るため)。

各ジョブのステップは次のとおり。

1. `actions/checkout`: リポジトリのコードをランナーに取り出す。
2. `pnpm/action-setup`: pnpm を入れる。版は `package.json` の `packageManager` から読む。
3. `actions/setup-node`: Node.js を入れる。版は `package.json` の `engines.node` から読む。版を YAML に書かないので、`package.json` と食い違わない。
4. `pnpm install --frozen-lockfile`: 依存関係を入れる。`--frozen-lockfile` は、`pnpm-lock.yaml` と `package.json` が食い違っていたら失敗させる指定である(ロックファイルの更新し忘れに気づける)。
5. チェックのコマンド(`pnpm lint` など)。

### キャッシュ

- **pnpm の依存関係**: `actions/setup-node` の `cache: pnpm` で、pnpm のストア(ダウンロードしたパッケージの置き場)を保存・復元する。キャッシュのキーは `pnpm-lock.yaml` の内容から作られるので、依存関係が変わると新しいキャッシュになる。
- **Turborepo のキャッシュは使わない**(オーナーが選んだ)。CI では毎回すべてのタスクを実行するので、「CI が成功した=今のコードで本当に全部通った」と言い切れる。いまの規模では、時間の差は小さい。パッケージが増えて遅くなったら、`actions/cache` で `.turbo` を保存する方法などを、改めて検討する。

### 権限と安全

- `permissions: contents: read`: トークンには、コードを読む権限だけを与える。既定の権限は広いことがあるので、明示して最小にする。必要なジョブが出てきたら、そのジョブにだけ権限を足す。
- `persist-credentials: false`: `actions/checkout` は、既定ではトークンを `.git/config` に残す。後のステップ(依存関係のスクリプトなど)から読まれないように、残さない。
- **アクションはコミットの SHA で固定する**: `v7` のようなタグは、公開している側があとから別のコミットに付け替えられる。乗っ取られたアクションに悪いコードを入れられても影響を受けないように、40桁の SHA で指定し、どの版かをコメント(`# v7.0.1`)で残す。
- `timeout-minutes: 15`: 何かが止まったときに、無料枠を使い続けないようにする。

### 古い実行の取り消し(`concurrency`)

`concurrency.group` が同じ実行は、同時に1つしか動かない。`cancel-in-progress: true` により、同じブランチに続けてプッシュすると、古い実行は取り消され、新しい実行だけが残る。グループの名前には `github.ref`(ブランチやプルリクエストを表す名前)を使う。

### 必須チェックにする

CI のジョブを必須にする設定は、ワークフローではなく、GitHub の画面(Settings → Rules → Rulesets)で行う。「Require status checks to pass」に、ジョブの名前(`lint`・`format`・`typecheck`・`test`・`build`、プルリクエストのタイトルを検査する `pr-title`)を登録する。`pr-title` は別のワークフロー([`.github/workflows/pr-title.yml`](../../.github/workflows/pr-title.yml))にある。詳しくは [commitlint と Conventional Commits](commitlint.md) を参照。
