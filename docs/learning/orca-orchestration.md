# Orca のオーケストレーション(複数のエージェントに分担させる)

## それは何か

オーケストレーションは、1人の「指揮役」のエージェントが、ほかのエージェント(作業役。Orca では worker と呼ぶ)を起動し、仕事を渡し、結果を受け取る仕組み。オーケストラの指揮者が演奏者をまとめるのにたとえた名前である。Orca では `orca orchestration …` のコマンドで使う(実験的な機能で、Settings → Experimental で有効にする)。

登場するものは次のとおり。

| 用語 | 意味 | このプロジェクトでは |
|---|---|---|
| Run | 1つの目的のための作業のまとまり。指揮役の受信箱(メールボックス)でもある | Issue 1件につき1つ |
| Task | Run の中の1つの仕事。ほかの Task の完了を待つ依存関係(`--deps`)も持てる | 「実装」「レビュー」 |
| Dispatch | Task を1人の作業役に割り当てた記録。ID(`dispatch:…`)で作業役を指定する | 実装役・レビュー役それぞれに1つ |
| worker | 作業役のエージェント。`worker-start` で、ワークツリーと一緒に起動できる | 実装役・レビュー役 |

やり取りは、エージェントどうしのメッセージで行う。

| コマンド | 誰が | 何をする |
|---|---|---|
| `worker-start` | 指揮役 | 作業役を起動して Task を渡す。`--worktree new-child` なら子ワークツリーも作る |
| `ask` | 作業役 | 指揮役に質問する。送ったらターンを終え、答えが届くと Orca が起こしてくれる |
| `reply` | 指揮役 | 質問に答える |
| `send` | 指揮役 | 作業役に追加の指示を送る。終わった作業役に送ると、新しい Task として受け取る |
| `send --type worker_done` | 作業役 | 「終わった」と、結果を報告する |
| `check` | 両方 | 届いたメッセージを読む |

## なぜ必要か

これまでは、オーナーが1つの Claude Code のセッションと話し、`/issue <番号>` の手順で実装からプルリクエストまでを進めていた。このやり方には、次の2つの困りごとがあった。

- **レビューが実装と同じ頭で行われる。** 実装した本人が確かめると、実装に合わせた甘い確かめ方になりやすい。
- **Issue を作る・ワークツリーを作る・レビューを頼む、といった段取りを、オーナーが手で回している。**

役割を分けると、レビュー役は実装を見る前に「合格の条件」を決められる(先に答え合わせの基準を作る、という考え方)。段取りは指揮役に任せられる。オーナーが話す相手は指揮役だけになる。

### 待ち方と利用枠

Claude Pro には利用枠(一定時間に使える量)がある。エージェントは、考えたり読んだりしているときだけ枠を使い、ターンを終えて何もしていないときは使わない。そこで、この仕組みでは次のようにする。

- **待つときはターンを終える。** Orca はメッセージが届くと、宛先のエージェントを起こしてくれる。指揮役が「まだ終わらないか」と何度も確かめる(ポーリング)と、そのたびに枠を使う。そのうえ、届いたメールを確かめる処理が横取りして、本来のエージェントに届かなくなることもある。
- **レビュー役は、チェックリストを作ったらいったん止まる。** 実装が終わったら `send` で起こし、続きをさせる。
- **作業役に読ませる仕様書の章を、指揮役が絞る。**

## このプロジェクトでどう使うか

オーナーが Claude Code で `/start <やりたいこと>` と入力すると、指揮役として次の順で進む。詳しくは [`docs/agents/`](../agents/) の3つの手順書と、[`AGENTS.md`「役割を分けて Issue を進めるとき」](../../AGENTS.md#役割を分けて-issue-を進めるとき)にある。

```text
オーナー ⇄ 指揮役(/start)
  1. Issue の案 → オーナーの承認 → gh issue create
  2. run-create → worker-start ×2(子ワークツリー issue-<番号>-impl・issue-<番号>-review)
       実装役: 標準の手順。計画は ask → 指揮役 → オーナー → reply
       レビュー役: 段階1 = Issue・仕様書・AGENTS.md だけでチェックリスト → worker_done
  3. 実装役が push の前で worker_done
  4. 指揮役 → レビュー役に send(段階2): 差分を検査し、わざと壊して確かめる
  5. 指摘があれば 指揮役 → 実装役に send で修正 → 4に戻る(2回まで)
  6. オーナーが push を承認 → 実装役が push・プルリクエスト・CI の確認
  7. レビュー役が、チェックリストと指摘の経過をレビューコメントにする
  8. 指揮役がまとめて報告 → オーナーがマージ → 片付け
```

### ワークツリーとブランチ

子ワークツリーは、同じリポジトリの別の作業フォルダなので、ブランチを共有している。そのため、レビュー役は push の前でも実装役のブランチを読める。

1つのブランチは、2つのワークツリーで同時に開けない(Git の制約)。そこでレビュー役は、`git switch --detach <ブランチ>` でブランチの「その時点のコミット」だけを開く(detached HEAD という状態)。この状態で何かを変えても、実装役のブランチには入らない。レビュー役はここで、テストが本当に効いているかをわざと壊して確かめ、終わったら元に戻す。コミットはしない。

### 試したこと(エージェントを起動しない範囲)

Issue #27 で、次を確かめた(Orca 1.4.247)。

```sh
orca orchestration run-create --objective "Issue #27 dry run: …"
orca orchestration task-create --task-title "dry-run implement" --spec "…"                       # → ready
orca orchestration task-create --task-title "dry-run review" --spec "…" --deps '["<実装の Task ID>"]' # → pending
orca orchestration task-list --ready --brief                 # 実装の Task だけが出る
orca orchestration task-update --id <実装の Task ID> --status completed
orca orchestration task-list --ready --brief                 # レビューの Task が出る
```

- 依存のある Task は、依存先が終わるまで `pending` のままで、`--ready` の一覧に出ない。
- 存在しない Task を依存先にすると、作成が拒否される。
- この試しの Run(`run_0c653547c912`)の記録は Orca に残る。消すには `orchestration reset` が必要だが、害はないので消していない。

この手順書では、レビュー役の待ち合わせに Task の依存関係を使わず、指揮役が `send` で段階2を渡す。レビュー役が段階1で考えた内容を覚えたまま検査できるからである(ADR 0024)。依存関係は、将来 Task を増やすときのために確かめておいた。

### 気をつけること

- 実験的な機能なので、コマンドが変わることがある。指揮役は始める前に `orca skills get orchestration` で最新の説明を確かめ、手順書と食い違えばオーナーに報告する。
- 実際に作業役を起動して動かすのは、フェーズ3-2(packages/db と Testcontainers による結合テスト)の Issue が最初になる。その結果をもとに手順を見直す。
