# モジュールの登録と境界

## それは何か

**モジュールの登録**は、「このアプリにどんな機能(モジュール)が載っているか」を、コアが外から教えてもらう仕組みである。各モジュールは自分の持ち物(API、画面、ツール、DBのマイグレーション、イベント、ジョブ)を**マニフェスト**という自己紹介の定義に書き、コアはそれを順に読んで組み込む。WordPress のプラグインや、VS Code の拡張機能と同じ考え方である。

**モジュールの境界**は、「モジュールの外から触ってよいのはここだけ」という線である。線の内側(テーブル、内部の関数)は、そのモジュールが自由に変えてよい。線の外に出すもの(公開用の入口、イベント)だけが、他のモジュールとの約束になる。

## なぜ必要か

- **追加しても既存を壊さないため**(spec §1.2)。コアが「家計簿」「カレンダー」という名前を知っていると、モジュールを足すたびにコアを直すことになる。コアが一覧を受け取って順に処理するだけなら、モジュールを足してもコアは変わらない。
- **変更の影響範囲を狭くするため**。家計簿のテーブルを他のモジュールが直接読んでいると、家計簿のテーブルを変えたときに、どこが壊れるかわからなくなる。境界を守っていれば、家計簿の中の変更は家計簿の中で完結する。
- **ルールは人が忘れるため**。「他のモジュールの内部を import しない」と文書に書くだけでは、いつか破られる。機械(型チェック、ESLint、テスト)に検査させると、破った瞬間に気づける。

## このプロジェクトでどう使うか

- マニフェストは2つある。サーバー用の `defineModule` と、画面用の `defineModuleUi`(ADR 0014)。画面はブラウザで動くので、DB のコードを混ぜないために分けている。
- 載せるモジュールは、`packages/registry/src/server.ts` と `apps/web/src/modules.ts` の2つの一覧に手で書く。自動で探すより、何が載っているかが一目でわかる。
- 名前の衝突は、モジュールの `id` を接頭辞にすることで防ぐ(`finance.add_transaction`、`/api/finance/...`、DB の `finance` スキーマ)。
- 他のモジュールの機能を使うときは、`@lifeos/<id>/public`(公開用の入口)だけを import する。起きたことを知らせるときはイベントを使う(ADR 0015)。
- 境界は3つの仕組みで検査する(ADR 0015)。
  1. **package.json の `exports`**: パッケージが外に出すファイルを限定する。書いていないパスは import できない。
  2. **ESLint の境界ルール**(eslint-plugin-boundaries): 「どの種類のファイルが、どの種類のファイルを import してよいか」を検査する。エディタの上で気づける。
  3. **アーキテクチャテスト**(dependency-cruiser と Vitest): 依存のグラフ全体や、SQL の中身など、ESLint では見えない約束を CI で検査する。
- 詳しい設計は [`docs/design/module-system.md`](../design/module-system.md) にある。
