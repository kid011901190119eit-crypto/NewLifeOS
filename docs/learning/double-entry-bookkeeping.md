# 複式簿記の仕訳と遅延制約

## それは何か
- **複式簿記**は、お金の動きを「どこから出て、どこへ入ったか」のペアで記録する方法。1つの取引を2行以上の**仕訳**に分け、各行に「どの勘定が、いくら増減したか」を書く。お金は消えたり湧いたりしないので、**1つの取引の仕訳の合計は必ず0**になる。
  - 例: 現金で食費800円 → 「現金 -800」「食費 +800」(合計0)
- **遅延制約(deferred constraint)**は、PostgreSQLの制約チェックを、1行ごとではなく**DBトランザクションのコミット時**にまとめて行う仕組み。`CREATE CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED` で作る。

## なぜ必要か
- 単式(1取引1行)だと、口座間の移動や貸し借りが「特別扱い」になり、計算のルールが場当たり的になる。複式なら、移動も貸し借りも開始残高も「勘定の増減のペア」という同じ形で扱え、残高は仕訳を足し合わせるだけで求まる。
- 仕訳は1行ずつ INSERT するため、1行目を入れた瞬間は合計が0にならない。普通の制約(即時チェック)では登録できないので、コミット時にチェックする遅延制約が要る。これで「合計が0でない取引」はアプリにバグがあってもDBに入らない。

## このプロジェクトでどう使うか
- 家計簿モジュールの `finance.transactions`(取引)と `finance.postings`(仕訳)。口座・ラベル・貸し借りの相手は、すべて `finance.accounts`(勘定)の行になる。
- 画面の入力(口座、金額、ラベル)は、アプリが仕訳に変換する。変換規則は [`docs/design/finance-data-model.md` §4](../design/finance-data-model.md)。
- 仕訳合計0の遅延制約トリガーは同じ文書の §5.2。フェーズ4で、合計が0にならない取引が拒否されることを Testcontainers の結合テストで確かめる。
- 判断の記録: ADR [0004](../adr/0004-double-entry-bookkeeping.md)、[0010](../adr/0010-finance-journal-rules.md)。
